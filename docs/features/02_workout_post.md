# 機能定義書：トレーニング記録投稿機能

## 1. 業務フロー

### 1-1. 投稿作成フロー
```
「投稿する」ボタンをクリック（タイムライン or FAB）
    │
トレーニング記録投稿画面（/workout-posts/new）を表示
    │
投稿情報を入力
    ├── タイトル（例: 「胸の日」）
    ├── トレーニング日（デフォルト: 今日）
    ├── 種目選択 → セット入力（重量・回数・メモ）× N セット
    ├── 種目追加（複数種目を追加可能）
    ├── 全体メモ
    └── 画像アップロード（最大 4 枚）
    │
「投稿する」ボタンをクリック
    │
    ├── バリデーションエラー → エラーメッセージ表示
    │
    └── バリデーション成功
            │
        POST /api/workout-posts でベース投稿を作成
            │
        画像がある場合: POST /api/workout-posts/:id/images でS3にアップロード
            │
        タイムライン画面（/）へ遷移
```

### 1-2. タイムライン閲覧フロー
```
タイムライン画面（/）を表示
    │
GET /api/workout-posts?page=1&limit=20 で投稿一覧を取得
    │
投稿カード一覧を表示（最新順）
    │
    ├── タブ「全体」← デフォルト（全ユーザーの投稿）
    └── タブ「フォロー中」← フォロー中ユーザーの投稿
    │
スクロールでページネーション（次のページを取得）
```

### 1-3. 投稿削除フロー
```
投稿詳細画面（自分の投稿）で「削除」をクリック
    │
確認ダイアログを表示（「この投稿を削除しますか？」）
    │
「削除する」をクリック
    │
DELETE /api/workout-posts/:id を実行
    │
バックエンドで DB の投稿・種目・セット・コメント・ナイスを削除
    │
バックエンドで S3 の画像ファイルも削除
    │
タイムライン画面（/）へ遷移
```

## 2. ユースケース

### UC-07: トレーニング記録投稿

| 項目 | 内容 |
|---|---|
| UC-ID | UC-07 |
| ユースケース名 | トレーニング記録投稿 |
| アクター | 認証済みユーザー |
| 事前条件 | ログイン済み |
| 事後条件 | 投稿が DB に保存され、タイムラインに表示される |

**基本フロー:**
1. 投稿作成画面を開く
2. タイトル・日付・種目・セット・メモを入力する
3. 必要に応じて画像を添付する（最大 4 枚）
4. 「投稿する」をクリックする
5. バックエンドが投稿・種目・セットを DB に保存する
6. 画像は S3 にアップロードし、image_key を DB に保存する
7. タイムライン画面へ遷移する

## 3. 機能要件

### 投稿データ仕様

| フィールド | 制約 |
|---|---|
| タイトル | 必須、1〜100 文字 |
| 全体メモ | 任意、500 文字以内 |
| トレーニング日 | 必須、過去日または当日 |
| 種目 | 最低 1 種目以上 |
| セット | 各種目に最低 1 セット以上 |
| 重量 | 0 以上（自重は 0） |
| 回数 | 1 以上 |
| セットメモ | 任意、200 文字以内 |
| 画像 | 任意、最大 4 枚、JPEG/PNG/WebP、各 10MB 以内 |

### タイムライン仕様

- ページサイズ: 20 件
- ソート: created_at DESC（最新順）
- 全体タイムライン: 全ユーザーの投稿
- フォロー中タイムライン: フォロー中ユーザー（自分含む）の投稿

### 投稿レスポンスに含まれる集計フィールド

`GET /api/workout-posts` および `GET /api/workout-posts/:id` のレスポンスには以下のフィールドが含まれる:

| フィールド | 型 | 説明 |
|---|---|---|
| likeCount | number | 投稿に付いたナイス数 |
| commentCount | number | 投稿に付いたコメント数 |
| isLiked | boolean | リクエストユーザーがナイス済みかどうか |

### 画像アップロード仕様

- アップロード方式: Multer + AWS SDK v3 サーバー中継（クライアント → バックエンド → S3）
- S3 key: `images/posts/{postId}/{uuid}.{ext}`（UUID で一意生成）
- DB には image_key のみ保存（URL は保存しない）
- 表示 URL の生成: `<IMAGE_BASE_URL> + "/" + image_key`
  - ローカル: `http://localhost:4566/<bucket-name>`
  - 本番: `https://<cloudfront-domain>`
- 投稿削除時は S3 の画像ファイルも連動削除

### フロントエンド画像バリデーション仕様（UX 向上目的）

最終検証はバックエンドが行う。フロントエンドはファイル選択直後に以下をチェックしてエラー表示する。

| 条件 | 処理 |
|---|---|
| 選択後の合計枚数 > 4 | 先頭から入る分だけ追加し超過分を除外。「最大4枚まで選択できます（X枚は除外されました）」を表示 |
| JPEG/PNG/WebP 以外 | 該当ファイルを除外しファイル名と理由をリスト表示 |
| 10MB 超過 | 該当ファイルを除外しファイル名と理由をリスト表示 |
| 0バイト | 除外し理由をリスト表示 |
| 重複（同名・同サイズ・同 lastModified） | 除外し「重複したファイルです」を表示 |
| 一部不正 | 有効ファイルのみを追加し送信を継続可能 |

### 投稿フロー（画像あり）の異常系

| 失敗地点 | 対処 | ユーザーへの通知 |
|---|---|---|
| POST /api/workout-posts 失敗 | 処理中止・ボタン再有効化 | フォームにエラーメッセージを表示 |
| POST /:id/images 失敗（投稿 DB は成功済み） | 投稿は維持。タイムラインへ遷移 | トースト「投稿は保存されましたが、画像のアップロードに失敗しました」（5秒後に自動消去） |

- 画像アップロード失敗後の再試行 UI は提供しない（投稿削除 → 再投稿で対応）

## 4. API 設計

| メソッド | エンドポイント | 説明 | 認証 |
|---|---|---|---|
| GET | `/api/workout-posts` | 投稿一覧取得（タイムライン） | 必要 |
| POST | `/api/workout-posts` | 投稿作成 | 必要 |
| GET | `/api/workout-posts/:id` | 投稿詳細取得 | 必要 |
| PUT | `/api/workout-posts/:id` | 投稿更新 | 必要 |
| DELETE | `/api/workout-posts/:id` | 投稿削除 | 必要 |
| POST | `/api/workout-posts/:id/images` | 画像アップロード（最大4枚） | 必要 |
| GET | `/api/exercises` | 種目マスタ一覧取得 | 必要 |
| POST | `/api/workout-exercises/:id/sets` | セット追加 | 必要 |
| PUT | `/api/exercise-sets/:id` | セット更新 | 必要 |
| DELETE | `/api/exercise-sets/:id` | セット削除 | 必要 |

### クエリパラメータ（GET `/api/workout-posts`）

| パラメータ | 型 | デフォルト | 説明 |
|---|---|---|---|
| page | number | 1 | ページ番号 |
| limit | number | 20 | 1ページあたりの件数 |
| feed | string | `all` | `all`（全体）または `following`（フォロー中） |
| userId | string | - | 指定ユーザーの投稿のみ取得（プロフィール画面用） |
